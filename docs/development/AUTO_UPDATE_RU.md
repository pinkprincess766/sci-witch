# Автообновление sci-witch

Статус: **в разработке**. Реализованы манифест и клиент обнаружения/скачивания с проверкой целостности. Установка, замена работающего приложения и интерфейс в трее намеренно не начинались — см. «Явно вне области этой задачи».

## Зачем

Тестеры получают переносимые ZIP-архивы, а не установщик — каждое обновление сейчас означает ручную скачку и переустановку. Цель: кнопка «Проверить обновления» в трее, которая показывает новую версию и краткий список изменений, и устанавливает — только после явного нажатия пользователя. Никаких тихих обновлений.

## Почему нужен собственный манифест, а не `/releases/latest`

Все выпуски sci-witch отмечены как `prerelease: true` (см. [release.yml](../../.github/workflows/release.yml)). Обычный endpoint GitHub `GET /repos/{owner}/{repo}/releases/latest` **не возвращает предварительные релизы** — так задокументировано в [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release). Поэтому нужен либо перебор списка релизов (`GET /repos/{owner}/{repo}/releases`, без `/latest` — он включает prerelease), либо собственный манифест. Выбран второй вариант: `update-manifest.json` собирается и публикуется как дополнительный файл релиза при каждой сборке.

## Формат манифеста

Генерируется в job `release` в [release.yml](../../.github/workflows/release.yml), публикуется как asset релиза рядом с ZIP-архивами.

```json
{
  "schema_version": 1,
  "version": "0.1.1-rc1",
  "channel": "preview",
  "published_at": "2026-09-01T14:52:04Z",
  "notes_url": "https://github.com/pinkprincess766/sci-witch/releases/tag/v0.1.1-rc1",
  "platforms": {
    "windows-x64": {
      "asset_name": "SciWhisper-0.1.1-rc1-Windows-x64.zip",
      "sha256": "<hex-64>",
      "url": "https://github.com/pinkprincess766/sci-witch/releases/download/v0.1.1-rc1/SciWhisper-0.1.1-rc1-Windows-x64.zip"
    },
    "macos-arm64": {
      "asset_name": "SciWhisper-0.1.1-rc1-macOS-arm64.zip",
      "sha256": "<hex-64>",
      "url": "https://github.com/pinkprincess766/sci-witch/releases/download/v0.1.1-rc1/SciWhisper-0.1.1-rc1-macOS-arm64.zip"
    }
  }
}
```

- `schema_version` — целое число; будущий несовместимый формат манифеста увеличивает его, а старый клиент, который его не понимает, обязан игнорировать релиз, а не падать.
- `version` — версия из тега без начальной `v`; CI перед публикацией проверяет её точное совпадение с `[workspace.package].version` из `Cargo.toml`. Клиент **должен** сравнивать её как SemVer (см. ниже про урок с `0.1.0` vs `0.1.0-rc1`).
- `channel` — сейчас всегда `"preview"`; канал `"stable"` появится только вместе со стабильными (не prerelease) выпусками.
- `url` — прямая ссылка на asset релиза; предсказуема из тега и имени файла, отдельный API-запрос за ней не нужен.
- `sha256` — считается в CI по уже собранному ZIP (`sha256sum`), не полагается на `digest`, который GitHub может не всегда отдавать для всех типов assets. Он обнаруживает повреждение или подмену ZIP относительно скачанного манифеста, но не заменяет цифровую подпись: манифест и архив публикуются в одном GitHub Release и имеют одну границу доверия.

## Как клиент находит и скачивает обновление

Реализовано в [`sciwhisper_shell::update`](../../crates/sciwhisper-shell/src/update.rs). URL из списка релизов и манифеста не используются как адреса запросов: они **восстанавливаются** из фиксированной базы репозитория, а пришедшие из сети значения сравниваются с ожидаемыми. Единственное исключение — заголовок `Location` при редиректе: он обрабатывается вручную с запретом смены схемы и ограничением числа переходов, как описано ниже.

1. `GET https://api.github.com/repos/pinkprincess766/sci-witch/releases?per_page=20` — фиксированный адрес, вшитый в клиент (список, **не** `/latest`, потому что `/latest` прячет prerelease).
2. Просматривается **вся** страница. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases) не документирует порядок выдачи как контракт, поэтому «первый в списке» ничего не значит: пропускаются `draft` и всё, что не `prerelease`, а из оставшегося выбирается **максимальный валидный SemVer**. Релиз не новее текущей версии пропускается, но **не завершает** поиск — иначе новый релиз, стоящий в выдаче позади старого, был бы не найден.
3. Дешёвый предфильтр по одному только списку: тег обязан иметь вид `v{SemVer}` и быть строго новее текущей версии, а `browser_download_url` ассета `update-manifest.json` — совпадать с **ожидаемым** URL вида `…/releases/download/{tag}/update-manifest.json`. Не совпал — релиз отброшен, **запроса за манифестом не было**. Кандидаты сортируются по убыванию версии, поэтому в обычном случае манифест скачивается ровно один.
4. Манифест запрашивается по восстановленному URL, а не по тому, что прислал API.
5. Манифест обязан быть внутренне согласованным, иначе релиз пропускается, а поиск продолжается со следующего по старшинству кандидата (то есть «максимальный **валидный**», а не просто «максимальный»):
   - `schema_version` и `channel` — поддерживаемые;
   - есть запись ровно для текущей платформы;
   - `version` парсится как SemVer и `tag_name == v{version}`;
   - `asset_name` равен `SciWhisper-{version}-{Windows-x64|macOS-arm64}.zip`;
   - `sha256` — ровно 64 hex-символа;
   - URL архива и `notes_url` совпадают с восстановленными из тега.
6. Версия сравнивается по SemVer. Не новее — значит нет обновления: равная версия не переустанавливается, старая не предлагается как откат.
7. Скачивание идёт во временный `.part`-файл **внутри** каталога назначения; конечное имя появляется только после полной загрузки и совпадения SHA-256. Существующий конечный файл не перезаписывается (`persist_noclobber`).

Платформы ограничены теми, что реально публикует workflow: `windows-x64` (`windows`/`x86_64`) и `macos-arm64` (`macos`/`aarch64`). Linux и другие архитектуры получают понятную ошибку и **не** подменяются macOS.

### Ограничения и тайм-ауты

| Что | Предел |
|---|---|
| список релизов | 2 МиБ |
| манифест | 256 КиБ |
| архив | 512 МиБ (реальные архивы ~3.5 МиБ) |
| соединение | 10 с |
| чтение / запись | 30 с каждое |

Размер проверяется дважды и независимо: сначала по заявленному `Content-Length` (ответ отклоняется до чтения тела), затем по фактически прочитанным байтам — для chunked-ответа, где `Content-Length` отсутствует вовсе. Сообщения об ошибке у этих двух проверок разные, чтобы было видно, какая сработала.

### Редиректы

Редиректы обрабатываются **вручную**, а не библиотекой: агент создаётся с `redirects(0)`, и каждый переход проверяется отдельно. GitHub отвечает на URL ассета редиректом на свой CDN, поэтому запрет редиректов сломал бы любое реальное скачивание, — но и молча принять переход `https://` → `http://` нельзя, это тихо снимает защиту транспорта.

Правило простое: схема каждого перехода обязана совпадать со схемой **начального** URL. Значит, понижение `https` → `http` отклоняется, как и переход на любую другую схему (`file:` и т. п.). Хост меняться может — иначе редирект на CDN был бы невозможен. Число переходов ограничено пятью, редирект без заголовка `Location` — ошибка.

Безопасным всё это делает то, что **начальный** URL никогда не берётся из ответа: он собран из вшитой базы и тега, обязанного иметь вид `v{SemVer}`, а манифест с расходящимися URL отклоняется до запроса. Манифест не может направить клиент на произвольный хост.

### Что даёт SHA-256, а что нет

SHA-256 — проверка **целостности** архива относительно манифеста: обрезанное, повреждённое или подменённое в пути тело будет отвергнуто. Это **не** цифровая подпись и не доказательство подлинности: манифест и архив лежат в одном GitHub Release, поэтому тот, кто может переписать релиз, перепишет оба согласованно. Эту брешь закрывает только подпись Developer ID / code signing.

## Урок про версии, который нельзя повторить

Первый опубликованный тег `v0.1.0-rc1` был собран с `Cargo.toml`-версией `0.1.0` (без суффикса). По SemVer `0.1.0` **новее**, чем `0.1.0-rc1` — сравнение версий сломалось бы для уже установленных тестеров. Исправлено переходом на `0.1.1-rc1` (см. [Cargo.toml](../../Cargo.toml)) — следующий выпуск обязан иметь числовую часть строго больше уже опубликованной, а не просто другой суффикс. Тег `v0.1.0-rc1` уже занят и повторно использоваться не может.

## Что реализовано

- манифест обновления генерируется и публикуется в каждом preview-релизе;
- release job прекращается до публикации, если версия `Cargo.toml` не совпадает с тегом;
- CI требует архивы с точной версией из тега и проверяет структуру готового манифеста;
- клиент обнаружения и скачивания ([`update.rs`](../../crates/sciwhisper-shell/src/update.rs)) со свойствами, описанными выше, и 29 регрессиями на локальном `tiny_http`-сервере: обнаружение новой версии, выбор максимальной версии в несортированном списке, продолжение поиска за релизом не новее текущего, откат к следующему кандидату при негодном манифесте старшего, следование редиректу в пределах схемы, отказ от понижения схемы, редирект без `Location`, предел числа переходов, защита от downgrade и повторной установки, несовпадение тега и версии, неверные schema/channel/platform, отклонение чужого URL манифеста **до** второго запроса, отклонение чужого URL архива **до** скачивания, `../victim.txt` не выходит из staging и не трогает соседний файл, повреждённый архив, превышение лимита с `Content-Length` и без него, обрыв чтения после частичной передачи, существующий ZIP не перезаписывается, и отсутствие `.part`/непроверенного ZIP после каждого отказа.

## Явно вне области этой задачи

Ничего из перечисленного не реализовано и намеренно не начиналось — это отдельные слои со своими рисками:

- распаковка архива (в том числе безопасная, в staging-каталог);
- helper-процесс Windows, закрывающий и перезапускающий приложение;
- замена работающей установки;
- откат (rollback) при неудачной замене;
- пункт «Проверить обновления» и любой интерфейс в трее;
- автоматическая периодическая проверка обновлений.

## Что ещё не сделано за пределами клиента

- на macOS: сначала только «скачать новую версию» (ad-hoc подпись означает, что автозамена может сбросить разрешения микрофона/Accessibility/Input Monitoring — см. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)); полноценная автозамена — только после стабильной Developer ID подписи;
- обновление [README.md](../../README.md) и [PRIVACY_RU.md](../user/PRIVACY_RU.md): проверка обновлений станет единственным сетевым запросом приложения, аудио и диктовка по-прежнему никуда не отправляются.
