# Канонический AST v1

`canonical_schema_version: 1`. Контракт заморожен: изменение правил ниже требует версии 2 и отдельного прогона — результаты разных канонизаций не смешиваются.

## 1. Зачем он нужен

Сравнение «правильно или нет» выполняется **по AST**, а не по строке вывода. Иначе два разных вопроса склеиваются в один:

* renderer выбрал `\left(` вместо `(` — это не научная ошибка;
* renderer сохранил формулу, но парсер поменял заряд — это ошибка, и одинаковый на вид вывод её не оправдывает.

Поэтому метрика AST и метрика вывода считаются раздельно.

## 2. Форма ключа

```
canonical_target_v1(RAW)      = "RAW"
canonical_target_v1(AST(node)) = "AST:" + canonical_node_v1(node)
```

`RAW` — **отдельное действие**, а не `Node::Text`, случайно попавший в пространство научных AST. Ключ `"RAW"` не может совпасть ни с одним ключом AST, включая AST, который сам является текстовым узлом.

`canonical_node_v1` — это serde-представление узла, сериализованное с **отсортированными ключами объектов**. Порядок ключей не зависит от того, в каком порядке поля объявлены в Rust-структуре.

## 3. Что сохраняется обязательно

Ни одно из этих различий не сглаживается:

| Различие | Пример |
|---|---|
| индекс | `H₂O` ≠ `H₃O` |
| коэффициент | `H₂O` ≠ `2H₂O` |
| заряд | `SO₄²⁻` ≠ `SO₄²⁺` |
| сторона реакции | `A → B` ≠ `B → A` |
| тип стрелки | `→` ≠ `⇌` |
| маркер состояния | `Cu(OH)₂` ≠ `Cu(OH)₂↓` |
| степень и показатель | `x²` ≠ `x³` |
| порядок производной | `df/dx` ≠ `d²f/dx²` |
| вид производной | `d` ≠ `∂` |
| направление предела | `x→0⁻` ≠ `x→0⁺` ≠ `x→0` |
| единица и её степень | `м` ≠ `с`, `м/с` ≠ `м/с²` |
| регистр и алфавит символа | `f` ≠ `F`, латинская `p` ≠ греческая `ρ` |
| группировка | `(a)` ≠ `a` |
| неявное умножение | `Juxt[a,b]` ≠ `Binary(Mul,a,b)` |

Последние две строки — сознательный выбор: скобка и неявное умножение несут смысл, который парсер обязан воспроизводить, а не «примерно угадывать».

## 4. Единственные разрешённые нормализации

Применяются только те переписывания, эквивалентность которых доказуема.

### 4.1 Документ из одного узла

```
Document([x]) → x
```

Все три renderer конкатенируют детей документа, поэтому `Document([x])` и `x` дают **побайтово одинаковый** вывод во всех форматах. Документ из двух и более узлов не трогается.

### 4.2 Десятичный разделитель числового литерала

```
Number("9,81") → Number("9.81")
Number("+7")   → Number("7")
```

Это одно и то же число. Оставшееся различие — типографика (русская запятая против точки), и за неё отвечает метрика вывода, а не метрика AST.

Литерал, который не является простым десятичным числом (`1e5`, пустая строка, `1.2.3`), не трогается вовсе.

**Практическое следствие.** `Number("9,81")` и `Number("9.81")` имеют один канонический ключ, но рендерятся по-разному (`9,81 м/с²` против `9.81 м/с²`). Такой случай классифицируется как severity `S0` — «только представление». Поэтому в корпусе для русской диктовки gold пишется с запятой.

## 5. Чего здесь нет

Алгебраические тождества **не применяются нигде**:

```
x/x        ≠ 1
√(x²)      ≠ x
log(ab)    ≠ log a + log b
a·1        ≠ a
Juxt[a,b]  ≠ Binary(Mul,a,b)
```

Это не CAS и не упрощатель. Канонизация приводит к общему виду **запись**, а не значение.

## 6. Границы и безопасный отказ

Вложенность глубже `MAX_CANONICAL_DEPTH = 128` не канонизируется: функция возвращает ошибку `TooDeep`, а не переполняет стек. Проверка глубины выполняется итеративно, поэтому измерение глубины само по себе не может переполнить стек. Кандидат, который не удалось канонизировать, выбрасывается из набора — он не может быть сравнён, значит не может считаться ответом.

## 7. Найденные архитектурные дефекты

Если два семантически одинаковых результата текущего парсера получают разные канонические ключи, это записывается как дефект, а не прячется эвристикой. На корпусе `dev-seed-v1` таких случаев **не обнаружено**: расхождения, которые нашла лаборатория, относятся к маршрутизации и к пробелам грамматики, а не к неоднозначной канонизации.
